What the store and endpoint own

One entry per club id app/actions/public/clubs/matches.ts

noneload(id)loading loading200 · stale fallback countsready loadingnetwork / 5xxerror errorretry → load(id)loading 
load(id)
  entry = entries.get(id)
  if entry is loading            // already in flight
    return
  if entry is ready and age < 1h  // age from server fetchedAt
    return
  set(id, loading)
  fetch(`/api/clubs/${id}/matches`)
    .then(json  → set(id, ready, json))
    .catch(()   → set(id, error))
  // set() dispatches 'change' with the id

Removing a club doesn't abort its request. The result stays in the store, so adding it back is instant.

The action rejects ids that aren't known clubs, so random ids can't burn upstream quota. The repository shares one in-flight promise per team id.

Still open

1. Clubs already in the cookie

Those cards need data on first load too. Either the client calls load for each follow after hydration, or the home action seeds fresh cache hits as initialMatches. Seeding is a DB read only and never calls upstream. Misses still go through the client path.

I lean: seed from cache
2. Error state

The header stays visible, plus "Couldn't load matches" and a retry that calls load(id). If the server falls back to stale cache, that counts as ready, not error.

I lean: header + retry
3. Upstream rate limit

Adding six cold clubs at once means six upstream calls. The known-club check and the in-flight dedupe keep that number from growing. I wouldn't add a client concurrency cap yet.

I lean: no cap for now
